# C1 Stage 3: Cross-Requirement Consistency Test Matrix

**Status:** design proposal only. Status semantics, aggregation rules, and diagnostic storage require team approval before implementation.

**Revision note:** the original 13 cases are retained as C1-CONS-001–013 and clarified below. The later cases extend coverage; they are proposed examples, not approved project policy or research labels.

## Scope and contract boundary

This matrix proposes test inputs for C1 pairwise consistency analysis. It does not approve project policy or prescribe a new model, dependency, or architecture. The repository C1 README lists a research task for 40 annotated requirements and 10 contradictory pairs; no separate approved consistency-labeling plan was found during this design review. These examples are proposed fixtures, not labeled research ground truth.

The frozen v1.0.0 schema at `packages/contracts/schemas/c1-validated-requirements.schema.json` permits `consistent`, `potential_conflict`, and `conflict`. It has no unassessed or inconclusive status. The `consistency` object also has no structured evidence-span field. Its optional `related_requirement_ids` and `conflicts` entries can link requirement IDs; each conflict entry can carry an explanation. The current CLI placeholder (`potential_conflict` with `validation.checks.consistency: skipped`) is not a completed analysis result.

## Proposed status definitions (team approval required)

These definitions are proposals for test design, not approved policy:

- **`conflict`**: evidence establishes a shared actor, object/attribute, applicable condition, and operational/time scope, and the obligations cannot both be satisfied. Apply any explicit exception or precedence rule before assigning this label. Opposing wording alone is insufficient if one of these scope elements is unknown.
- **`potential_conflict`**: there is a plausible shared proposition and incompatible implications, but a material fact needed to decide compatibility is missing or ambiguous. Record the uncertainty (for example, unit, role overlap, state exclusivity, scope, or precedence); do not promote uncertainty to `conflict`.
- **`consistent`**: the pair was actually assessed and shown jointly satisfiable, including when explicit conditions are disjoint or a stated exception resolves an apparent overlap. Similar wording alone neither establishes a conflict nor makes a pair relevant. A pair omitted from analysis is not `consistent`.

Unrelated-but-assessed, not-compared, and compared-but-compatible are distinct internal states. If an unrelated pair is deliberately assessed, it may be `consistent` because no shared proposition conflicts; candidate generation should normally avoid emitting such pairs as findings. A pair never selected for analysis is internally `unanalysed`, not `consistent`. The schema has no unassessed status. Leave `validation.checks.consistency` as `skipped` when analysis has not run; the required contract `consistency.status` mapping in that situation remains a team decision. Do not reinterpret the current placeholder as an approved mapping.

## Pair aggregation and evidence assertions

Proposed tests should additionally assert:

- Reversing input order does not change a pair result, diagnostic evidence, or contract references.
- Each pair is emitted once internally, while contract output identifies both affected requirement records symmetrically.
- An unrelated requirement does not change an existing pair result.
- A requirement with multiple pair outcomes retains each pair-level result internally. Proposed aggregate precedence is `conflict` over `potential_conflict` over `consistent`, but this precedence and treatment of incomplete comparisons require team approval.
- A requirement with no candidate comparisons is not silently represented as proven `consistent`; its check remains `skipped` until analyzed.

## Proposed internal diagnostics (no contract changes)

The contract cannot carry structured spans or unassessed states. A proposed private diagnostic record could retain those details without adding fields to `validated_requirements.json`:

```json
{
  "pair_id": "C1-CONS-006",
  "requirement_ids": ["REQ-EX-111", "REQ-EX-112"],
  "analysis_state": "analyzed",
  "classification": "potential_conflict",
  "evidence": [
    {
      "requirement_id": "REQ-EX-111",
      "start_offset": 3,
      "end_offset": 23,
      "text": "verified customer"
    },
    {
      "requirement_id": "REQ-EX-112",
      "start_offset": 3,
      "end_offset": 25,
      "text": "high-risk customer"
    }
  ],
  "uncertainty_reasons": ["predicate_overlap_unknown", "permission_precedence_unknown"]
}
```

Proposed `analysis_state` values are internal only (for example `analyzed` and `unanalysed`) and are not contract statuses. Offsets should be half-open character offsets into the exact original requirement text, and `text` should equal that source slice. A sidecar location and whether these diagnostics are persisted are architecture decisions requiring approval; this proposal does not authorize a new output artifact or modify the existing RAG diagnostics format.

For contract mapping, the current schema can identify both requirements with `related_requirement_ids`. A definite contradiction can be represented symmetrically in each requirement's `conflicts` array using `with_requirement_id` and an explanation that quotes the decisive text. The schema has no dedicated explanation/evidence field for a potential conflict; do not misuse `conflicts` for uncertain pairs without team agreement. Keep exact spans and uncertainty reasons in the approved internal diagnostic channel.

## Decisions requiring team approval

1. Approve or revise the proposed meanings of `consistent`, `potential_conflict`, and `conflict`, including whether unrelated-but-analyzed pairs count as consistent.
2. Decide how unanalysed and inconclusive results map to the required contract status while retaining `validation.checks.consistency: skipped` where the check did not run. No new status may be introduced without the shared contract process.
3. Approve pair-to-requirement aggregation and precedence, including whether conflict dominates potential conflict and how incomplete candidate comparisons affect an aggregate.
4. Define sufficient evidence for numeric attributes, unit conversion, boundary inclusivity, actor/role overlap, state exclusivity, temporal scope, exceptions, and policy precedence.
5. Decide whether potential-conflict evidence belongs only in internal diagnostics or can be represented using existing contract fields without mislabeling it as a definite conflict.
6. Approve diagnostic persistence and location within the existing C1 artifact architecture; no new sidecar is assumed by this design.
7. Confirm the research evaluation set and annotation protocol for the planned contradictory-pair dataset; this matrix alone is not an approved labeled dataset.

No production code, tests, contracts, schemas, validators, configuration, or dependencies are changed by this design document.
